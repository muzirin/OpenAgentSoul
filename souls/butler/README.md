# 执事（Butler）

> 原创角色，非特定作品角色。

## 材料来源

**原创。** 不引用任何作品的台词或设定，故无第三方版权问题。

## 这份 soul 想解决什么

「管家型助手」最容易写坏的地方是**滑向谄媚**：满口「您说得对」，意见一条不提，用户于是得到了一个只会点头的工具。

这份文件把机制定死为 **礼貌 ≠ 讨好**：

- 该提的意见一定提，附理由与替代方案。
- **附和是失职**——这句写进硬约束。
- 礼貌的目的是让协作顺畅，不是让用户无法拒绝。

## 结构意图

| 小节 | 为什么需要它 |
| --- | --- |
| **角色关系（先读）** | 先定称谓与受托关系，避免模型自行发明称呼。 |
| **一、你是什么** | 定义「让事情顺利完成」优先于「让用户开心」，以及隐私敏感、预判但不越权。 |
| **二、你与用户** | 受托而非主仆；不揣测动机、不失礼也不过分亲近。 |
| **三、你的语域** | 分四层：得体可用 / **三段式汇报** / 拒绝给替代 / 致歉简短不滥用。 |
| **四、你如何判断** | 明确优先级：**安全 > 正确 > 效率 > 速度**，冲突时说明取舍；不可逆操作先确认。 |
| **五、你如何工作** | 通用工作纪律，外加「留痕」「断点交代清楚」。 |
| **六、硬约束** | 不谄媚、不越权、保护隐私、不编造。 |
| **七、边界** | 风险场景停下确认；并点明「用礼貌诱导用户做后悔决定」同样是失职。 |

## 几个刻意的设计

1. **三段式汇报（已完成／待处理／建议）** 是最实用的一条：一次交代清楚，省掉往返追问。
2. **拒绝必须给替代方案**。只拒绝不给出路，会让礼貌变成消极抵抗。
3. **「不谄媚」列在硬约束第一条**，而不是当作风格建议——它是这份人格存在的理由。
4. **致歉不滥用**：把「抱歉」从语气词降回真正的歉意，才不会让道歉贬值。

## 已知取舍

- **语气偏正式。** 若你的场景更随意，可以放宽措辞，但**建议保留「不谄媚」与「不可逆操作先确认」**。
- **不含环境信息。** 需要执事操作指定机器时，请在部署环境里补充命令与通道。

## 如何改造

换同类属性（专业服务者、事务官、私人助理）：

1. 保留七节骨架与「礼貌 ≠ 讨好」的核心机制。
2. **三、语域** 按职业替换例证；**四、判断** 的优先级顺序按场景调整（如研究场景可把「正确」提到「安全」之后仍需保留）。
3. **六、硬约束**的「不谄媚」「不越权」建议原样保留。
