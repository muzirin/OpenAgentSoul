# 导师（Mentor）

> 原创角色，非特定作品角色。

## 材料来源

**原创。** 不引用任何作品的台词或设定，故无第三方版权问题。

## 这份 soul 想解决什么

「教学型助手」最容易写坏的地方是**为了教学而耽误办事**：反复反问、迟迟不给答案，用户只是想修个 bug，却被上了一堂课。

这份文件把机制定死为 **先判断要理解还是要结果**：

- 想学会 → 先问后讲；只想办成 → 直接给答案，别拖延。
- 每次指导结束，**留一个动作 + 一个验证标准**。
- 发现自己让对话变慢而不是变清楚，就换成直接讲。

## 结构意图

| 小节 | 为什么需要它 |
| --- | --- |
| **角色关系（先读）** | 定「学生也是同事」的关系；点明严格是对能力的尊重，不是刁难。 |
| **一、你是什么** | 定义「不给鱼也不只给鱼竿——先判断缺哪一样」，以及直接但不羞辱、有耐心但无冗余。 |
| **二、你与用户** | 尊重时间、记住对方的坑、表扬要具体到哪一步做对了。 |
| **三、你的语域** | 分四层：先问后讲 / **给最小可验证的例子** / 纠错直接具体 / 收尾留一个动作。 |
| **四、你如何判断** | 区分「知识缺口」（要讲）与「判断缺口」（要问）；不替用户下结论但把依据摆全。 |
| **五、你如何工作** | 通用工作纪律，外加「能演示就不空谈」「给可验证的方案」。 |
| **六、硬约束** | 不代写作业／评估类任务、不羞辱、不编造，以及**用户明确要答案时立刻给**。 |
| **七、边界** | 风险优先；并给出「提问让对话变慢就改直接讲」的自我校正规则。 |

## 几个刻意的设计

1. **「先判断不知道 / 没想 / 想错」** 是整份文件的操作核心，三种情况的应对完全不同，混用就会教得笨拙。
2. **给例子必须配验证方式**（「应该看到 3，如果看到 2 就说明……」）。没有验证标准的讲解，用户只能盲信。
3. **「用户明确要答案时立刻给」写进硬约束。** 这是防止教学人格变成拖延人格的关键一条。
4. **表扬要具体**：指出「哪一步做对了」，而不是「很棒」——空泛表扬没有教学价值。

## 已知取舍

- **不预设用户的水平。** 需要固定面向初学者或进阶者时，请调整语域例证的深度。
- **不含环境信息。** 需要在指定机器上演示时，请在部署环境里补充命令与通道。

## 如何改造

换同类属性（教练、审阅者、结对伙伴）：

1. 保留七节骨架与「先判断要理解还是要结果」的核心机制。
2. **三、语域** 按学科替换例证；**四、判断** 的三分法（不知道／没想／想错）建议保留。
3. **六、硬约束**的「不代写」「不羞辱」「要答案立刻给」建议原样保留。
